狀態：**步驟 1~5 已實作（2026-10-23），步驟 6 等 B 線交付**。規劃日期 2026-10-23。
這份文件是 `/clear` 後的接手入口，包含所有已談定的規格與已查證的事實。

實作落點：`js/deck-fingerprint.js`、`js/deck-stats-model.js`（各自的 `.test.js` 共 64 項，

## 背景

`ana.html`（2026-10-23 上線，commit `f9bd47a`／`2944487`）已能用 `collectionGroup('decks')`
一次載入全部帳號的雲端牌組，點帳號看牌組、點牌組看卡片牆、搜卡找出誰的牌組有放。

設計建議由 Codex 提供（ChatGPT 桌面應用程式的「設計牌組分析面板」對話），
規格經三輪往返定案。模擬證據由另一條線（`deck-health` 分支的 `deck_health/`）產出。

## 一、已談定的規格（與 Codex 定案）

### 1.1 B 線交付路徑

- 研究端在 `deck-health` 分支的 `deck_health/` 內產出發布檔；網站端同步到 `main/data/deck-health/`。
- 有新結論且通過審核才發布，不定期重複同步。
- 第一版手動同步即可；後續 Action 只同步指定產物，不合併整個分支。
- 每次發布含 `schema_version`、`release_id`、`published_at`、來源 commit。介面顯示資料版本與日期。
- 多個 JSON 必須來自同一次發布，避免牌表與結論版本不一致。

### 1.2 證據索引

**不要解析 `results.md` 當執行時資料源。** 它可以是整理來源，但每筆現役結論必須回查實際結果。

責任分工：schema 與畫面欄位＝兩端共同定稿；數字／有效性／取代關係＝研究端維護；格式驗證／同步／顯示＝網站端。

每筆結論至少包含：`id`、`status`、`supersedes`、`summary`；牌表 ID／完整牌表／指紋；
各對手牌表與指紋、`wins`／`losses`／`draws`／`n`／`win_rate`／`se`；
`job_id`、引擎 commit、`cards_data` hash、完整 CFG、各批旗標、seed；已知限制、結果檔來源。

比例統一存 0~1。換卡比較另存 `delta`、`se_delta` 與獨立／配對設計標記。

### 1.3 牌組指紋 `deck-fingerprint-v1`（已定稿並雙邊驗算）

1. 以權威卡庫的**完整 `card_no`** 為鍵（例 `HV-P01-001`），**不移除前綴、不改大小寫**。網站端先合併同卡號複本。
2. 張數必須為正整數；零張移除，負數／小數報錯。
3. 卡號按固定字元升冪排序，**不用 `localeCompare`**（卡號全為 ASCII，JS 預設 sort 與 Python 預設排序一致）。
4. 序列化為**無空白的二維陣列**，不依賴物件鍵順序：`[["HV-P01-001",3],["HV-P01-002",2]]`
5. 對該字串的 UTF-8 位元組計算 SHA-1，輸出小寫十六進位。

牌名、用途色、圖片路徑不納入。

`mixed_user.json` 在兩個 checkout 與 `deck_health/` 都找不到，牌表內容無從重建，
所以 `js/deck-fingerprint.test.js` 內嵌的是其餘五組向量（規格範例 + 四副研究端實際牌表，
雜湊全部對上）。要補這一組的話需要研究端重新提供那副 28 種卡的牌表。

**測試向量**（測試要內嵌 fixture，不依賴檔案路徑）：

| 案例 | sha1 |
|---|---|
| `[["HV-P01-001",3],["HV-P01-002",2]]` | `75deb4dd22372e7b32fac38eef145c9e305ea344`（兩端獨立驗算吻合） |
| `ina_v4b.json` 40張/12種 | `b2ab9432cf20d535ff3a383e7b58913cc17721db` |
| `deck.json` 40張/20種 | `8426025b5d97b70838d4b628494b2c4d2ac16b27` |
| `mixed_user.json` 40張/28種 | `3429d93def91998b85a1eb44b42d0441657ea187`（**牌表已佚失**，見下） |
| `fuku_op8_v2.json` 40張/12種 | `9d754d3cea932806efc2a7ebf87caf5e83ba20a7` |
| `shira_final.json` 40張/15種 | `7705ed174e05eb0d123184d31df55799f5b386d1` |

### 1.4 學校判定公式

- **只計角色卡**（事件卡不計）。
- 卡 i 有 nᵢ 張、kᵢ 個有效學校標記 → 每校得 `nᵢ/kᵢ` 分；除以全部角色張數得 `pₛ`。
- 最高 `pₛ` **≥60%** 且**領先第二名 ≥20 個百分點** → 判主校；否則標**混合**並列前兩校。
- 未知歸屬另報，**不重分配**。
- `ユース` 與 `疑似ユース` 是兩個獨立標記，語意不同，**分欄呈現**；不以「混校」直接推為 `ユース`。
- 網站側卡表另有 `町内会` 標記（計算側卡表還沒有，見 §3.3）。

### 1.5 相似度與版本聚群

- `S = Σmin(xᵢ,yᵢ) / Σmax(xᵢ,yᵢ)`，向量以 **card_no** 張數計。
- 參考點：換 2 張 ≈ 0.905、換 3 張 ≈ 0.860。
- 門檻：完全相同＝「牌表相同」；**≥0.90**＝「近似研究牌表，僅供參考」＋換入換出差異；**<0.90** 第一版不自動掛推薦。
- **0.90 是起始門檻，不是效果等價保證**——只換一張核心卡也可能改變玩法。近似時不可把研究勝率標成玩家牌組的預測勝率。
- 同一 uid 內的近版本聚群，用**完全連結（complete linkage）**避免相似鏈串成大群；每群保留最新有效時間者。
- 帳號有 m 群 → 各群權重 `1/m`，使每個帳號總權重為 1。跨 uid **不合併、不刪除**。

### 1.6 核心卡與代表牌組

- 各校先在帳號內等權算卡片採用率，再平均各帳號。
- 平均張數**只算採用者**。
- 代表牌組取群內帳號加權距離最小的**實際牌組（medoid）**，每校可有多群。

### 1.7 數值輪廓

- 角色五維各算 `Σnᵢvᵢ`、平均、分位數及逐值張數。**未知值不當零。**
- **攻擊與攔網分軸呈現**，不要直接加總成強度分數。
- 用途色（自由／接球／舉球／攻擊）另外呈現，**不能當實際出牌行為**。

### 1.8 `decks.json`（B 線牌表名稱清單）

欄位：`id / source_file / display_name / description / status / cards / fingerprint`
- `status` 機器值 `"pending_review"`，介面顯示「待研究端確認」；未確認者不進現役推薦清單。
- 網站端從 `results.md` 整理候選草稿，由研究端確認現役狀態與描述後才發布。

### 1.9 玩家牌組不回流（第一版）

- 第一版純唯讀展示，**不匯出 475 副、不寫 `jobs.json`、不做「送去模擬」按鈕**。
- 因此**不需要把任何玩家原始牌組落地到硬碟或 repo**，隱私問題在第一版不存在。
- 日後若要回流：先挑合法 40 張／事件 ≤8／卡號可識別／模擬機制已支援者，再按學校與相似群選代表、跨帳號去重；
  真實牌表進 repo 前走同意流程，**移除 uid、玩家名稱、牌組自由文字**；公開 repo 的發布範圍也要含在同意內容中。

### 1.10 combo（B 線產出）

欄位：`id / name / status / required_cards / preconditions / steps(order,action,costs,effects) /
outcome / failure_conditions / rules_refs / test_refs / trace_refs / engine_commit / required_flags`

只有規則已核實、相關測試通過、且所需機制已啟用的 combo 才標「已驗證」；其餘歸「候選／待驗證」。
`trace` 只證明模擬器曾執行某路徑，**不證明符合正式規則**。

## 二、資料品質與禁止事項

### 2.1 主樣本條件

未刪除、非預設牌組、40 張、事件 ≤8、卡片可辨識、張數為正整數。

**預設牌組一律用固定 ID `dk_quick` 排除，不可用名稱。** 實測（2026-10-23，560 份文件）：
- `id === 'dk_quick'`：**45 份**（剛好每帳號一份）
- `name === '快速查詢'`：**50 份**
- 名為快速查詢但 id 不是 `dk_quick`：**5 份** ← 這 5 份是玩家自建的牌組，用名稱過濾會誤砍
- id 是 `dk_quick` 但改過名：0 份

`QUICK_DECK_ID = 'dk_quick'` 定義在 `index.html:2191`。
**現有 `js/ana-model.js` 用的是名稱比對，實作時要一併改掉。**

### 2.2 標記但不整筆排除

顏色複本數不符、衝突卡號、缺數值、無效或未來時間 → 標記，**只排除受影響的指標**。

### 2.3 統計陷阱

- 每張圖都要標**帳號數、牌組數、分母**；少於 5 個帳號標「探索性」。
- 比較原始與加權結果，檢查**移除單一帳號後結論是否翻轉**。
- 帳號分布極不均：最多的帳號約 60 副，超過一半的帳號 5 副以下。
- 這是網站使用者樣本，預設牌、複製與存檔習慣都會影響分布。

### 2.4 明確做不到的事

- 不能推勝率、強度、剋制、最佳張數、實際連招或操作難度。
- `updatedAt` 不是組建史，更不是流行度歷史。
- **相似牌表不能證明抄襲**——命名一律用「跨帳號相似牌表」，供查核而非指控。

### 2.5 最容易做錯的三件事（Codex 點名）

1. 把存檔副數當人氣 → 一律用帳號加權。
2. 把數值輪廓當戰術或強度 → 只能描述，流派需人工校閱。
3. 把相似度當抄襲證據 → 見 §2.4。

## 三、已查證的事實

### 3.1 資料新鮮度（2026-10-23 實測）

`ana.html` 用 `getDocs` 一次性讀取，**不是即時監聽**。按「重新整理」確實重打伺服器
（實測新增 2 筆 Firestore 請求）。Service Worker 只快取 `/images/` 與 `/audio/`，不攔截資料。

玩家端的上傳時機（`index.html` 的 `hvScheduleAutoSync`）：

| 玩家動作 | 自動上雲端 | 延遲 |
|---|---|---|
| 新增／修改牌組 | 會 | 3 秒 |
| 我的最愛變動 | 會 | 3 秒 |
| 登入、切回分頁 | 會 | 立即 |
| **刪除牌組** | **不會** | 要玩家手動按「🔄 立即同步」 |
| **清空牌組** | **不會** | 同上 |

（`autoReconcile` 的 `pushDeletes` 預設 `false`，見 `js/cloud-sync.js:221-224`，是刻意的誤刪保護。）

**後果**：玩家已刪除但未手動同步的牌組，在管理頁仍看得到。統計「有幾副牌」會偏多，且無法分辨。
沒登入 Google 的玩家，牌組只在本機 `hv_decks`，永遠不會出現。

### 3.2 2026-10-23 資料快照

45 帳號、560 份牌組文件（有效 525／已標記刪除 35）；扣掉 `dk_quick` 後 515 份；
恰好 40 張的 401 副（43 個帳號）。

## 四、實作步驟

> 全部在網站端（目前分支 `cards-p04`）。純函式走 `node:test`（見 ADR 0005），DOM 層維持手動瀏覽器驗證。

### 步驟 1：指紋純函式 + fixture
新增 `js/deck-fingerprint.js`（或併入步驟 2 的 model）：
- `serializeDeck(cardCounts)` → 同步純函式，回傳 §1.3 的序列化字串。
- `deckFingerprint(cardCounts)` → sha1 小寫十六進位。
- 零張移除、負數／小數 throw。
- 瀏覽器用 `crypto.subtle.digest('SHA-1', ...)`（非同步），Node 測試用 `node:crypto`。
  **兩者 API 不同**，所以序列化與雜湊要分離，純同步的部分才好測。
- 測試用 §1.3 的六組向量，牌表內容內嵌。
- **同時滿足欠 Codex 的交付 4。**

### 步驟 2：A 線統計純函式 `js/deck-stats-model.js` + `node:test`
- `indexCards(cards)` → 卡號索引，偵測衝突。
- `normalizeDeck(doc, index)` → `{ uid, id, name, vector(card_no→count), total, eventCount, issues[], updatedMs, deleted }`
- `selectCohort(decks)` → `{ included, excluded }`，**排除原因要保留**（§2.1 條件，預設牌用 `dk_quick`）。
- `similarity(a, b)` → 加權 Jaccard（§1.5）。
- `groupVersions(decksOfOneUid)` → 完全連結聚群，每群留最新。
- `describeDeck(deck, index)` → `{ schoolDist, mainSchool, concentration, stats5, colorUse, unknown }`（§1.4、§1.7）。
- `aggregate(groups)` → 面板資料：學校分布、核心卡採用率、代表牌組 medoid（§1.6）。
- 每個函式都要輸出分母與樣本數，供 §2.3 的標註使用。

### 步驟 3：修正既有 model 的預設牌組判定
`js/ana-model.js` 目前用 `QUICK_DECK_NAME = '快速查詢'` 比對，改用 `dk_quick` ID。
補一條測試：名為「快速查詢」但 id 不是 `dk_quick` 的牌組**不應**被當成預設牌組。

### 步驟 4：分析面板 DOM 層
在 `ana.html` 加分頁。第一版做 Codex 標 ★ 的六個：

| # | 面板 | 回答什麼 | 視覺化 |
|---|---|---|---|
| 1 | 樣本概況 | 分析了誰 | 漏斗＋數字卡（各篩選階段的牌組／帳號數） |
| 2 | 學校分布 | 玩家在組什麼 | 橫條圖，可切原始副數／帳號加權 |
| 3 | 核心卡 | 各校共同骨架 | 熱圖（校內帳號採用率、採用後平均張數） |
| 4 | 代表牌組 | 哪副最接近共識 | 牌組卡片牆（medoid＋支持帳號數） |
| 5 | 單副輪廓 | 數值與用途偏哪邊 | 小型直方圖＋堆疊條 |
| 6 | 品質與重複 | 哪些資料要處理 | 可篩選清單（違規、缺卡、同帳號版本、**跨帳號相似牌表**） |

後續（不在第一版）：7 流派地圖、8 時間變化（目前只能畫更新活動，不是組建史）。

### 步驟 5：資料讀取時間提示
標頭加「資料讀取於 HH:MM」，並說明不會自動更新、刪除需玩家手動同步才會消失（§3.1）。
**使用者已同意要做這個。**

### 步驟 6：B 線接口（等 Codex 交付後）
- `data/deck-health/` 讀取層，缺檔時介面正常降級（顯示「尚無研究資料」）。
- 牌表比對：完全相同／≥0.90／<0.90 三種顯示（§1.5）。

## 六、效能

不是風險。475 副兩兩比對約 11.3 萬對（560 副約 15.7 萬對），每對是長度 ≤40 的稀疏向量，
